# 阶段执行提示词 · W1 → W12

> 每个阶段开始时,在项目根目录新开一个 Claude Code 会话,粘贴对应小节 `---` 之间的全部内容。
> 每完成一个阶段,手动更新 `CLAUDE.md` 末尾的「当前阶段」。

**通用前置**:所有提示词都假设 `CLAUDE.md`、`docs/PLAN.md`、`docs/SPEC.md` 已在仓库中。Claude Code 会自动加载 `CLAUDE.md`,但需要显式要求它读 SPEC。

## W1–2 · 地基

---

# 阶段任务:W1–2 地基

先读 `docs/PLAN.md` §3、§7、`docs/SPEC.md` 全文、`report/M1-勘测报告.md`。读完先用三句话复述 M1 的路线判定结论,确认理解一致后再动手。

## 目标

把数据契约和提取能力落地。本阶段**不写任何 patcher**。

## 任务

### T1 · 仓库初始化
- 按 `docs/PLAN.md` §11 建立完整目录结构
- 根目录 `LICENSE` 为 MIT,`corpus/LICENSE` 为 CC0-1.0(下载官方全文,不要自己写)
- `.gitignore` 覆盖 CLAUDE.md R2 列出的全部模式
- `SECURITY.md` 按 `docs/PLAN.md` §8 撰写
- README 第一屏严格按 `docs/PLAN.md` §2.2,对照效果块放在所有徽章之前

### T2 · schema 落地
- `schema/unit.schema.json` 与 `schema/glossary.schema.json` 已提供,直接使用,**不要修改**
- 写 `schema/validate.py`:校验任意 corpus 文件,输出人类可读的错误定位(文件、unit id、字段、原因)

### T3 · 核心库
在 `corelib/` 下实现 `docs/SPEC.md` §1、§2 的算法:
- `normalize(s)`、`extract_placeholders(s)`、`unit_id(s)`、`display_width(s)`
- **必须写单元测试,覆盖 SPEC §1.3 的全部测试向量**,hash 值必须完全一致
- 这些函数一旦有实现偏差,后续所有语料都会作废,测试不通过不许进入 T4

### T4 · 提取器
- `extractors/js-ast/`:解析 JS,提取字符串字面量 + 所在上下文(用于风险分类)。目标是 `cli@2.1.112` 和 Desktop 的 asar
  - 文件很大,先评估 AST 解析是否 OOM,必要时降级为流式扫描
- `extractors/binary/`:二进制字符串提取,输出内容、字节偏移、字节长度
- 两者统一输出 `extracted/<target>-<version>.jsonl`

### T5 · 风险分类器
- `classifiers/` 实现 `docs/SPEC.md` §6 的规则表,规则编号写入 `risk_reason`
- 输出三个队列:`excluded` / `candidates` / `unknown`
- **规则 6 命中输出 UNKNOWN,不是 SAFE**。这一点如果实现错了,整个 fail-safe 机制就失效了

### T6 · CI 骨架
`.github/workflows/` 建立:
- `validate.yml`:corpus 的 schema 校验 + `docs/PLAN.md` §7.1 全部八项检查
- `test.yml`:corelib 单元测试
- 两个 workflow 必须在本阶段就能跑通(哪怕 corpus 还是空的)

### T7 · 首份语料
- 用 T4 + T5 处理 `cli@2.1.112` 和 Desktop,产出 `corpus/cli/2.1.112.json`、`corpus/desktop/<版本>.json`
- **全部 unit 的 risk 保持分类器给出的值,一条译文都不要填**
- 按 `docs/SPEC.md` §9 格式,units 按 id 字典序排列

## 交付物

```
corelib/(含测试)  schema/validate.py  extractors/  classifiers/
corpus/cli/2.1.112.json  corpus/desktop/*.json
.github/workflows/  LICENSE  corpus/LICENSE  SECURITY.md  README.md
docs/W1-2-总结.md
```

## 完成标准(DoD)

- [ ] corelib 单元测试全绿,SPEC §1.3 测试向量逐条一致
- [ ] 两个 CI workflow 在 GitHub 上实际跑通
- [ ] `python schema/validate.py corpus/` 零错误
- [ ] 首份语料生成,分类统计写入 `docs/W1-2-总结.md`(各 risk 等级条数、candidates 队列规模)
- [ ] `git status` 干净,`samples/` 和 `extracted/` 未被追踪

## 红线提醒

不要为了让 corpus "看起来有内容"而填任何译文。本阶段的语料**应该是全空译文的**。

## W3–4 · Desktop 首发

---

# 阶段任务:W3–4 Desktop 首发

先读 `CLAUDE.md`、`docs/SPEC.md` §5.2、`docs/W1-2-总结.md`。

## 目标

发出 v0.1.0,Windows 端 Claude Desktop 可用。**这是项目第一个面向用户的产物,一次失败会永久损伤信任。**

## 任务

### T1 · 人工审阅 candidates 队列
- 从 Desktop 的 candidates 队列中挑选**高频可见**的界面文案优先处理(设置页、主界面、菜单、常见错误提示)
- 逐条确认 risk,确认无误的升为 SAFE 并填 `target`
- 本阶段目标 **300–600 条**,不追求覆盖率,追求零错误
- 遇到吃不准的一律留 UNKNOWN

### T2 · 术语词表起步
- 建立 `corpus/glossary.json`,本阶段先收录 **80–120 词**
- 严格按 `docs/PLAN.md` §4.1 / §4.2 判据填 `reason`
- 同步生成 `target_bilingual`,遵守 `docs/SPEC.md` §7 的**单条最多 2 个标注**限制

### T3 · Desktop patcher
`patchers/desktop-asar/`:
- 探测安装路径(Windows 两种路径都要覆盖:`%LOCALAPPDATA%\AnthropicClaude\app-*` 与 WindowsApps)
- **打补丁前强制备份,备份路径打印到终端**
- 解包 → 注入 zh-CN 资源 / 替换硬编码文案 → 重打包
- 检测到 Claude Desktop 正在运行时,提示用户关闭,**不要强杀进程**
- `restore` 命令完整还原,并校验还原后文件的 SHA256 与备份一致

### T4 · CLI 入口
`claude-zh` 命令实现:
```
claude-zh install desktop [--mode=zh|bilingual]
claude-zh restore desktop
claude-zh status
```
`status` 显示:检测到的安装路径、当前是否已打补丁、补丁版本、备份是否存在。

### T5 · 冒烟测试
`verifier/` 实现 `docs/SPEC.md` §5.2 的 D1–D4。D4 视觉回归先建立基线截图。

### T6 · 发布
- GitHub Actions 构建,**禁止本地打包上传**(CLAUDE.md R6 / PLAN §8.1)
- release asset 附 SHA256
- release notes 写明:支持的 Desktop 版本、已知不支持的平台、还原方法

## DoD

- [ ] 在干净的 Windows 环境实测:安装 → 使用 → 还原,全流程无残留
- [ ] 故意制造一次失败(如中途断开),验证自动还原生效
- [ ] D1–D4 全绿
- [ ] release 由 CI 构建,SHA256 可校验
- [ ] README 的对照效果截图用**真实运行截图**替换掉占位

## 红线提醒

如果 macOS 因签名问题无法可靠工作,**在支持矩阵中标注"暂不支持",不要发布勉强能跑的版本**。首发的可靠性比覆盖面重要得多。

# 阶段任务:W5–6 CLI A 层

先读 `CLAUDE.md`、`docs/PLAN.md` §3.1、§4。

## 目标

在**完全不修改 Claude Code** 的前提下,做出可见的中文化效果。同时把术语词表补到 300 词。

## 任务

### T1 · 官方扩展点盘点
先实地确认当前版本 Claude Code 支持哪些扩展点,把结果写进 `docs/extension-points.md`:
- statusline 自定义
- hooks
- 自定义 slash command
- output style / CLAUDE.md 注入
- 插件机制

**以实测为准,不要依赖记忆或旧文档。** 每一项都要实际配置一次并确认生效。

`patchers/cli-layer-a/`:

### T3 · 术语词表补齐到 300 词

### T4 · CLI 语料审阅

### T5 · 扩展入口

## W7–8 · 自动化流水线

---

# 阶段任务:W7–8 自动化流水线

先读 `docs/PLAN.md` §6、`docs/SPEC.md` §4、§8。

## 目标

**这是整个项目最重要的阶段。** 没有流水线,前面所有语料会在两个月内腐烂。优先级高于任何功能开发。

## 任务

### T1 · 版本探测
`.github/workflows/watch.yml`,每 6 小时:
- 查 npm registry 的 `@anthropic-ai/claude-code` 最新版本
- 查 Desktop 更新源
- 与 `corpus/` 中已有版本比对,有新版本则触发 T2

### T2 · 自动提取与 diff
- 隔离下载新版本(`npm pack`,绝不 install)
- 跑提取器 + 分类器
- 按 `docs/SPEC.md` §4 执行继承算法
- **重点实现 surface 变化检测**:surface 变了的 unit 必须重新分类,不得直接继承 SAFE

### T3 · SAFE 复检
对所有现存 `risk == SAFE` 的 unit 重跑规则 1–5(SPEC §6)。任一命中 → 降级 + 清空 target + 在 PR 中高亮告警。

这一步防的是「某个字符串从 UI 挪进了 prompt」这类静默污染,是流水线里最容易被省略、也最不能省略的一环。

### T4 · LLM 预翻译
- 只对 `candidates` 队列调用,用 `docs/SPEC.md` §8 的 prompt,**一字不改**
- `confidence < 0.8` 的条目在 PR body 中单独列出
- 绝不对 DANGER / FRAGILE 调用

### T5 · 自动 PR
PR body 必须包含:
```
新增 N 条 / 继承 M 条 / 降级告警 K 条 / 消失 J 条
低置信度条目清单(逐条列出 id + source + 建议译文 + note)
风险降级告警清单(必须人工确认)
```
- 打 `automated` 标签
- **绝不自动合并**

### T6 · 发布流水线
合并后自动:构建 patch → 跑冒烟测试 → 通过则发 release → 更新支持矩阵。任一失败终止并开 issue。

### T7 · 支持矩阵自动生成
`docs/support-matrix.md` 由脚本生成,禁止手工维护。按 `docs/PLAN.md` §9 的策略标注 EOL。

## DoD

- [ ] 用一个历史版本做端到端演练,验证继承率(应 > 85%)
- [ ] 人为构造一条 SAFE→DANGER 的降级场景,验证 T3 能捕获
- [ ] 自动 PR 实际产生过至少一次,格式符合要求
- [ ] 支持矩阵自动生成且内容正确

## 红线提醒

流水线不得自动合并任何 PR。自动化的目的是把人工审阅量从数千条降到数十条,**不是取消人工审阅**。

## W9–10 · CLI 深度适配

---

# 阶段任务:W9–10 CLI 深度适配

先读 `report/M1-勘测报告.md` §2 的路线判定、`docs/SPEC.md` §3。

## 前置判定

**根据 M1 结论选择路线,不要两条都做:**

| M1 结论 | 本阶段做什么 |
|---|---|
| C 路线可行 | 走 T-C 系列(二进制 patch) |
| C 路线不可行 | 走 T-B 系列(PTY 拦截) |
| 两者都不可行 | **跳过本阶段**,把时间投入语料覆盖率和 Desktop 完善,在 `docs/` 中记录结论 |

## T-C 系列:二进制 patch

### T-C1 · 最小改动验证(强制前置)
严格执行 `docs/SPEC.md` §3.3:
1. 选一条 spinner 动词,用等字节 ASCII 替换
2. 跑三条冒烟测试
3. 再验证「补 `\x00`」与「补空格」两种缩短方案

**任一失败 → 立即停止 C 路线,转 T-B。** 不要试图绕过,不要批量试错。

### T-C2 · 存储形式判定
按 SPEC §3.2 确定字符串在二进制中的存储形式,写入 `docs/binary-layout.md`。

### T-C3 · patcher 实现
- 严格遵守 `byte_budget`,超预算的 unit 直接跳过并记录
- 打补丁前备份原二进制
- 打完后立即跑冒烟测试,失败自动还原

### T-C4 · 自动更新对抗
Claude Code 自动更新会覆盖补丁。实现检测机制,发现版本变化时提示用户重新打补丁。**不要自动重打**,不要拦截官方更新。

## T-B 系列:PTY 拦截

### T-B1 · 原型验证
- 用 PTY 启动真实 `claude`,拦截 stdout
- 先做**零替换透传**,确认 TUI 完全正常(颜色、光标、重绘、窗口 resize)
- 透传都做不到就不用继续了

### T-B2 · 等显示宽度替换
- 只替换满足 `display_width(target) == display_width(source)` 的条目
- 宽度不等的一律跳过
- 实测错位情况,量化记录

### T-B3 · 可用性判定
连续使用 30 分钟,记录错位次数。**错位频繁到影响使用就如实判定失败**,在文档中记录并放弃 B 路线。

## DoD

- [ ] 选定路线的冒烟测试全绿
- [ ] 失败自动还原经过实测验证
- [ ] 若路线判定为不可行,`docs/` 中有明确结论和数据支撑

## 红线提醒

本阶段最容易出现的错误是**为了让路线"成功"而降低标准**。C 路线的最小验证失败就是失败,B 路线错位严重就是不可用。如实记录失败比勉强交付有价值得多——`docs/PLAN.md` §7.3 的分层降级机制就是为此设计的,A 层永远兜底。
