# RUNBOOK · 运行手册

> 项目进入执行期后的日常参考。**决策树部分是预先约定的判定规则,遇到分叉时照此执行,不要临场重新论证。**

## 1. 决策树

### 1.1 M1 结论 → 后续路线

| M1 观测 | 判定 | W9–10 做什么 | 语料策略 |
|---|---|---|---|
| 二进制中能定位到多数已知 UI 文案,明文可读 | C 路线可行 | 二进制 patch | CLI 目标覆盖率 70% |
| 只能找到零星字符串,UI 文案大量缺失 | C 路线覆盖不足 | 优先试 B 路线,B 失败则跳过 | CLI 目标覆盖率 40% |
| 几乎找不到可读 UI 文案(bytecode 化) | C 路线不可行 | 只做 B 路线 | CLI 目标覆盖率 30% |
| Desktop i18n 结构清晰、zh-CN 资源位存在 | Desktop 走填空 | — | Desktop 目标覆盖率 85% |
| Desktop 大量文案硬编码在 JS chunk | Desktop 需混合策略 | — | Desktop 目标覆盖率 60% |

### 1.2 单条字符串该不该翻译

```
这条字符串会被发给模型吗?(tool description / system prompt / 参数说明)
├─ 是 或 不确定 → DANGER,不翻译
└─ 否
   └─ 代码里有地方拿它做比较或匹配吗?
      ├─ 是 或 不确定 → FRAGILE,不翻译
      └─ 否
         └─ 我能明确说出它显示在界面的哪个位置吗?
            ├─ 不能 → UNKNOWN,留待审
            └─ 能
               └─ 译文显示宽度 ≤ 原文?
                  ├─ 否 → 换更短译法;换不出来则 UNKNOWN
                  └─ 是 → SAFE,可翻译
```

**每一个"不确定"都指向不翻译。** 这不是保守,是因为误翻 DANGER 类的代价(agent 静默退化、难以归因)远大于少翻一条的代价。

### 1.3 术语该不该保留英文

```
它是 Claude 的产品功能名吗?(compact / Plan mode / subagent)
├─ 是 → 保留,reason=PRODUCT_NAME
└─ 否
   └─ 用户可能拿它去搜索或提 issue 吗?(报错信息、状态名)
      ├─ 是 → 保留,reason=SEARCHABILITY
      └─ 否
         └─ 官方文档里高频出现且中译名会对不上吗?(hook / MCP / skill)
            ├─ 是 → 保留,reason=DOC_FREQUENCY
            └─ 否
               └─ 中文语境里本来就直接说英文吗?(token / commit / prompt)
                  ├─ 是 → 不加括号,zh 直接写英文,reason=ALREADY_EN
                  └─ 否 → 纯中文,reason=GENERIC_UI / COMMON_TECH / STATUS_WORD
```

### 1.4 补丁在某平台失败

```
是本项目的实现问题吗?
├─ 是 → 修
└─ 否(平台限制:签名、权限、文件占用)
   └─ 有可靠的规避方案吗?
      ├─ 有 → 实现,并在文档中说明额外步骤
      └─ 没有 → 支持矩阵标"不支持",不发布勉强能跑的版本
```

**绝不通过降低冒烟测试断言来让某平台"通过"。**

## 2. 必须停下来的情况

以下情况**不要自行决定**,停下来交给人判断:

| 情况 | 为什么 |
|---|---|
| 需要修改 `schema/` | 数据契约变更会影响全部历史语料 |
| 需要放宽 `verifier/` 的断言 | 断言是质量底线,放宽等于放弃保护 |
| 要把 DANGER / FRAGILE 降为 SAFE | 需要实测证据和人工确认 |
| 官方新版本结构大幅变化 | 需要重新评估路线,不是打补丁能解决的 |
| 发现 corpus 出现可疑改动 | 可能是投毒,需要审计 |
| 收到任何法务相关通知 | 按 `docs/PLAN.md` §13.2:立即下架,不抗辩 |
| 冒烟测试 S3 持续失败且原因不明 | 说明 SAFE 白名单有系统性错误 |
| 周投入连续超过 25 小时 | 触发 `docs/PLAN.md` §13.2 的范围缩减评估 |

## 3. 日常任务提示词

### 3.1 新版本适配

```
新版本适配任务。

先读 CLAUDE.md 和 docs/SPEC.md §4、§6。

1. 确认自动流水线的 PR 已生成。若未生成,手动触发 watch workflow 并排查原因。
2. 审阅 PR:
   - 风险降级告警清单 → 逐条核实,这是最优先项
   - 低置信度译文(confidence < 0.8) → 逐条改或退回 UNKNOWN
   - 新增 UNKNOWN 条目 → 从高频可见的开始处理,不追求全部处理完
3. 确认继承率。低于 80% 说明规范化或提取器可能有问题,先查原因再继续。
4. 本地跑冒烟测试(SPEC §5),全绿才合并。
5. 合并后确认发布流水线跑通,支持矩阵已更新。

遇到吃不准的条目一律留 UNKNOWN。不要为了提高覆盖率而降低判定标准。
```

### 3.2 审阅待审队列

```
审阅 UNKNOWN 队列。

先读 CLAUDE.md、docs/RUNBOOK.md §1.2、corpus/glossary.json。

从 <target> 的 UNKNOWN 队列中取 <N> 条,按 RUNBOOK §1.2 的决策树逐条判定。

要求:
- 每条给出判定结果和依据(规则编号或一句话说明)
- 判为 SAFE 的,同时给出 target 和 target_bilingual
- 译文遵守 docs/PLAN.md §5 的风格规范和 §4.3 的对照格式
- 涉及新术语的,同步更新 corpus/glossary.json
- 吃不准的保持 UNKNOWN,并在 notes 里写明疑虑

处理完提交前先跑 python schema/validate.py corpus/ 和全部 CI 检查项。
```

### 3.3 处理用户 bug 报告

```
处理 issue #<编号>。

先读 CLAUDE.md。

1. 从报告中提取:OS、Claude 版本、patch 版本、claude-zh status 输出
2. 判断类别:
   - 补丁导致 Claude 不可用 → 最高优先级,先确认用户能还原,再排查
   - 某处未翻译 → 查该字符串在 corpus 中的 risk,若是 DANGER/FRAGILE 则如实说明这是刻意不翻译
   - 补丁失效 → 查是否版本更新导致,引导重新安装
   - 显示错位 → 查 display_width 约束是否被违反
3. 若属于 SAFE 白名单错误(即误翻了不该翻的),立即:
   - 把该 unit 降级
   - 检查同类字符串是否有相同问题
   - 发修复版本
   - 在 docs/metrics.md 记录一次「严重事故」
```

### 3.4 月度指标更新

```
更新 docs/metrics.md。

统计并记录:
- 各 target 的 SAFE 覆盖率、UNKNOWN 队列规模
- 本月新版本数量、平均适配耗时
- 外部贡献者数量、合并的外部 PR 数
- 严重事故次数(打补丁导致不可用)
- 本月实际投入工时

然后对照 docs/PLAN.md §13.2 逐条检查退出条件,如实给出结论。
如果任一条件触发,明确写出来,不要淡化。
```

## 4. 故障排查

### 4.1 打完补丁 Claude Code 起不来

**立即执行 `claude-zh restore code`。** 确认用户恢复正常后再排查。

排查顺序:
1. 是否改了长度前缀型字符串却没同步改长度字段(SPEC §3.2)
2. 是否误翻了 FRAGILE 类(被代码匹配的字符串)
3. 是否破坏了二进制的对齐或校验和
4. macOS:是否是签名问题而非补丁本身

定位方法:**二分法**。把本次改动的 unit 分成两半,只应用一半,逐步缩小到具体条目。不要靠猜。

### 4.2 打完补丁 Claude Desktop 起不来

1. 正常退出 Claude，不要由补丁器结束进程。
2. 执行 `claude-zh restore desktop`。
3. 确认输出包含原始 SHA-256 已验证，再启动 Claude。
4. 保存 `claude-zh status`、Claude 版本和备份路径用于排查。

若安装中途报错，补丁器会自动执行同样的逐文件还原。MSIX 不进入此流程：检测到 MSIX 时必须在写入前停止，并报告 `msix-unsupported`。

### 4.3 S3 冒烟测试失败(能启动能对话,但工具调用出问题)

**这是最危险的信号,说明误翻了 DANGER 类字符串。**

1. 立即停止发布
2. 用二分法定位到具体 unit
3. 定位后不要只修这一条 —— 查它是怎么通过分类器的,补分类规则
4. 对全部 SAFE 重跑复检(SPEC §6)
5. 在 `docs/metrics.md` 记录事故

### 4.4 继承率暴跌(< 80%)

按可能性排序:
1. 提取器输出变了(新版本结构变化)
2. `normalize()` 实现被改动 → 跑 SPEC §1.3 测试向量确认
3. 官方大规模重写了文案(真实情况,但少见)

**先跑测试向量。** 如果测试向量不一致,说明是实现问题,不是官方改动。

### 4.4 二进制格式变了,C 路线失效

1. 重跑 SPEC §3.3 的最小改动验证
2. 通过 → 只是偏移变了,更新 patcher
3. 不通过 → 在支持矩阵标注该版本"C 层不支持",A/B 层继续生效
4. 连续两个版本不通过 → 触发 `docs/PLAN.md` §13.2,评估是否永久放弃 C 路线

### 4.5 Windows 文件被占用

不要强杀进程。检测到占用时提示用户手动关闭,给出具体的进程名。

### 4.6 macOS Gatekeeper 拦截

不要引导用户关闭 SIP 或全局禁用 Gatekeeper。只提供针对本应用的处理指引,并在文档中说明这么做的含义。**如果找不到用户可接受的方案,标注 macOS 不支持。**

### 4.7 用户报告"某些地方还是英文"

先查该字符串的 risk:

- `DANGER` / `FRAGILE` → **如实说明这是刻意的**,翻译会导致功能异常。这是项目的设计,不是缺陷
- `UNKNOWN` → 加入待审队列
- `SAFE` 但未生效 → 查 patcher 是否因 `byte_budget` 超限跳过了

在 FAQ 中固定写一条解释,避免重复回答。

## 5. 六个月检查点

W26 执行,逐条对照 `docs/PLAN.md` §13:

**指标核对**

- [ ] SAFE 覆盖率 ≥ 90%?
- [ ] 新版本 6h 内自动 PR?
- [ ] 外部贡献者 ≥ 3?
- [ ] 双端均有稳定 release?
- [ ] 严重事故 = 0?
- [ ] 词表 ≥ 300 且一致性 100%?

**退出条件核对**

- [ ] 官方是否已推出中文界面? → 若是,归档并把 CC0 语料贡献上游
- [ ] 是否连续 2 个版本无法适配? → 若是,停止跟进新版
- [ ] 周投入是否持续 > 25 小时? → 若是,砍掉 CLI C 层或暂停 Desktop
- [ ] 外部贡献者是否为 0? → 若是,上游定位证伪,降级为自用工具

**诚实核算的提醒**

这一步最容易自我欺骗。六个月的沉没成本会让人倾向于把"还行"读成"成功"。判断标准是:如果这是别人的项目,你看到这组数据会建议他继续投入吗?

如果答案是否定的,就按 §13.2 执行,不要拖。主动收尾比烂尾体面得多,而且 CC0 语料本身就是留给社区的东西,不会白做。
