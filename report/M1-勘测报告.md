## 1. 执行摘要

1. Claude Code 2.1.220 原生二进制中能找到多条已知 UI 文案的完全匹配，明文没有整体 bytecode 化，CLI 二进制 C 路线在技术上可行。
2. 同一短字符串在二进制中可能出现几十到上百次，裸字符串扫描还会把 PE 机器码误判为文本；C 路线必须先定位真实字符串表和全部引用，不能直接批量替换。
3. CLI 2.1.112 的 13.7 MB JS bundle 可用 Acorn 完整解析，未 OOM；但单次 AST 解析 RSS 约 936 MiB，流水线需要按文件隔离并预留内存。
4. Desktop 已具备完整的本地化加载和运行时切换机制，但应用语言目录只有 11 种语言、没有中文；主界面又分布在 asar 外的 772 个 Web JS chunk 中，不能靠新增一个 `zh-CN.json` 完成。
5. Desktop 应采用“本地化 JSON 填充 + asar 壳层 + Web chunk 分析”的混合策略；Microsoft Store/MSIX 版本还有签名和安装目录权限问题，不适合作为首个可写补丁目标。

## 2. 路线可行性判定

| 路线 | 目标 | 判定 | 依据 |
|---|---|---|---|
| A 官方扩展点 | CLI / Desktop | **部分可行** | CLI 明确暴露 hooks、plugins、output format、settings 等入口；Desktop 暴露 locale 初始化与运行时切换 IPC。它们能提供低风险覆盖，但无法替换全部核心 UI。 |
| B PTY 拦截 | CLI | **部分可行** | CLI 输出可以被管道/重定向捕获，官方 `--print` 也明确支持 pipes；本轮未做交互式 ConPTY 原型，Ink 重绘和 CJK 双宽错位仍未验证。 |
| C 二进制 patch | CLI | **可行，高风险候选** | 2.1.220 原生二进制中找到 `auto-accept edits`、`Continue`、`Permission denied`、`Thinking`、`Photosynthesizing` 的完全匹配；但重复副本和噪声很多，必须保留最小等字节修改验证作为强制前置。 |
| C asar / 资源 patch | Desktop | **部分可行，必须混合实现** | 应用级语言 JSON 和运行时切换机制完整；但没有中文资源，且主要 UI 还存在于 asar 外的 52.2 MB Web chunks。MSIX 签名和写权限使直接修改已安装包风险较高。 |

结论：保留原规划的分层降级，但调整实现预期。

- CLI：A 层作为稳定地基，B 层继续原型验证，C 层保留为可选高覆盖增强。
- Desktop：不能仅按 `app.asar` patch 设计；需要同时处理应用资源 JSON、asar 壳层与 `ion-dist` Web 资源。首发应优先调查非 MSIX 分发形态。

## 6. 意外发现

1. 当前 Claude Code 最新 npm 主包已经是极小 wrapper，真正二进制完全位于平台 optional dependency 中；原规划对此判断正确。
2. 原生二进制有大量短字符串重复副本，`Continue` 完全匹配达 138 次。二进制提取器必须保留 occurrence，而 corpus 只按规范化 ID 去重。
3. 任务给出的简单 UI 启发式会大量命中 PE 机器码；二进制 extractor 需要区分 executable section、data section 和 Bun snapshot。
4. Desktop 当前版本把资源分散在 `app.asar`、`app.asar.unpacked`、应用级 JSON、`ion-dist` 四处，结构比规划中的单一 asar 更复杂。
5. Microsoft Store 版的应用目录本轮可读，但写入会涉及权限、MSIX 完整性和签名；不应作为第一个 patcher 验证目标。
6. 本机没有系统 Python。W1–2 若把 Python 作为用户侧运行依赖，需要明确最低版本和 Windows 安装方式，或者将探针/安装器打包为自包含产物。
7. 当前目录尚未初始化为 Git 仓库，因此本轮只能验证 `.gitignore` 内容，不能验证 tracked files 或 CI。

## 7. 对 W1–2 的具体建议

### 7.1 中间提取记录与 corpus 分离

不要把所有 occurrence 塞进 `unit.schema.json`。建议：

- `extracted/*.jsonl` 保存 `source`、`offset`、`byte_length`、`encoding`、`container`、`section`、`context`
- corpus 继续按规范化 `id` 去重
- patcher 使用 `id -> occurrences[]` 中间索引定位同一 unit 的全部副本

这样既保持 corpus diff 可审阅，又能支撑二进制多副本修改。

### 7.2 二进制 extractor

- 先解析 PE section，默认排除 executable code section 中的随机可打印字节
- ASCII 与 UTF-8 分开统计，但合并连续合法文本
- 同时输出 occurrence count 与唯一字符串数
- 对已知 UI 文案分别记录 exact hit 和 containing hit
- 不把“形似 UI”直接提升 SAFE

### 7.3 JS AST extractor

- 继续采用真正 AST，而不是正则替代
- 单文件单进程解析，避免多个 1 GiB AST 并发
- AST 只在内存中遍历，输出紧凑 JSONL，不序列化完整 AST
- 保留 property、call argument、comparison、switch case 上下文
- 将本轮 20 条人工样本扩成持续回归集，特别覆盖两个误报

### 7.4 Desktop extractor

Desktop extractor 需要三个独立入口：

1. `app\resources\<locale>.json`
2. `app.asar` / `.vite` renderer
3. `app\resources\ion-dist\assets`

语言 JSON 的 key 是哈希 ID，需通过英文 value 和 AST 调用点共同确定 `surface`。

### 7.5 分类器

本轮数据验证了 fail-safe 设计的必要性：

- `R-UITEXT` 只能进入 candidates
- DANGER / FRAGILE 永不产出 target
- 二进制来源比 JS AST 来源采用更严格阈值
- Desktop Web 层需额外识别 tool description、prompt suggestion 和普通 UI 的区别

### 7.6 冻结 schema 前先解决契约冲突

按 PLAN，M1 后应冻结 schema；但冻结前需要用户确认以下问题，本轮未修改 schema：

1. `unit.schema.json` 的 `placeholders.uniqueItems: true` 不允许同一占位符重复出现，而 SPEC 要求按出现顺序保存原文；例如同一字符串两次出现 `{0}` 时两者冲突。
2. SPEC 的 `extract_placeholders()` 对原字符串分别运行所有正则，`${name}` 会同时被 `${...}` 和 `{name}` 两个模式命中，可能重复计数。
3. Schema 示例中的 `Continue?` ID 与 SPEC 的正式测试向量不一致；冻结前应统一示例。

建议先写契约测试并由用户批准修订，再冻结 `$id` 和格式版本。
